Problem 4:
In looking at this program it does have good SOLID principles to it. But when we come into a functional programing domain we see that there are a few 
hidden issues in regards to the effects and mutability of this program. The first example of a hidden effect of this program is the call to self.repo.get_name(id).
When we think of functional programming we want functions that given a single input it will always return the same output. In this case we cannot always say this is true.
As we do not know if the get_name function in this case will always return the same with a given ID. If this is calling into a DB or an API or even just a class member.
We can not for certain say it will return the same due to changes in the DB, not connecting to the API, etc etc.
In the since of mutablility we have the &self. In rust this is saying hey there is no mutation here. But deep down there could be underlying mutation to the user service/repo.
This can be hidden behind a mutex or an Arc deeper down. When we think about this for functional we want to remove any ability to manipulate the data and just be able to read only on the data.
